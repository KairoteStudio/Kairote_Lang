# Kairote Lang 内存模型:三块制(safe / scope / unsafe)

> 状态：**三块制为设计方向；Re.KrtC 已实现 unsafe 指针子集**（实现基线见 §6）
> 本文档是内存管理的权威设计文档;`Lang_Spec.md` §内存管理 与此同步。

## 1. 设计总纲

内存管理按**三个互斥的代码块**组织,每个块对应一种检查强度与运行时行为:

| 块 | 目标 | 机制 |
|---|---|---|
| `unsafe(using ...)` | 指针与底层内部函数的可控使用 | 命名空间白名单 + 硬边界 |
| `scope` | 自动内存管理 | 编译期活性扫描 + 自动插释放 |
| `safe` | 泄漏风险提示 | 轻量级静态检查,只警告 |

核心立场:**不实现后台 GC 线程**。自动性由编译期完成("用起来跟 GC 差不多"),
运行时只有显式插好的释放命令。

## 2. unsafe 块

```KrtL
unsafe(using 公司名.产品名.功能模块;) {
    // 指针操作
    // 底层内部函数调用
}
```

### 2.1 适用对象

- **指针操作**
- **库内部函数**:指以 `_` 开头、原本不作为公开 API 暴露的底层函数。
  公开 API 不受此机制约束。

### 2.2 白名单机制

- 括号内的 `using` 列表是**命名空间白名单**(形如 `公司名.产品名.功能模块`)。
- 只有白名单中的命名空间,其内部函数才允许在本块内调用;
  未列入白名单的,**即使项目已引用该库也不给调用**。

### 2.3 硬边界(编译器强制,非约定)

- unsafe 块内的指针**不得操作块外的内存**;
- 违反即为**编译期硬错误**,不是警告——防止悬垂指针随指针值逃逸出块。
- 三块之间禁止互相嵌套,同类块也禁止自嵌套。

## 3. scope 块

```KrtL
scope {
    var obj = new MyClass();
    // ...
}   // obj 的释放在此处由编译器自动插入
```

### 3.1 语义

块内代码占用的内存被**统一管理**。效果等同 GC:
某段内存在某个阶段之后**彻底无人使用**时,释放命令被及时插入到该点。

### 3.2 实现路线(裁决)

- **不做后台 GC 线程**;
- 采用**编译期静态扫描**:先分析出各内存的死亡阶段,
  再在产出的代码里自动穿插释放命令;
- 即:自动内存管理的效果,编译期插桩的实现。

## 4. safe 块

```KrtL
safe {
    // 普通代码
}
```

- 只做**轻量级静态检查**:潜在内存泄漏风险
  (如循环引用、事件未解绑之类);
- 查出即报**警告**,不阻止编译。

## 5. 待裁决清单

以下问题在设计落地前需逐条裁决(本文档不擅自定案):

1. **默认态**:顶层/函数体中不写任何块的代码,按 safe 处理还是独立第四态?
2. **unsafe 边界精确化**:"指针操作到外面的内存"的判定基准——
   是指针**值**逃逸出块即错,还是**解引用目标地址落在块外**即错?
3. **scope 逃逸语义**:`return` 出 scope 块的对象算"仍有人用"(移交所有权)
   还是违规?
4. **既有设施归位**:`delete` 语句、标准库 `Memory.Allocate/Free`
   在三块制下的可用范围(是否仅限 unsafe/scope?)。
5. **内部函数归属判定**:`_` 前缀函数所属命名空间以何为准——
   声明处所在命名空间,还是需要显式标注?
6. **白名单粒度**:using 列到"功能模块"级即可,还是允许列到单个函数?

## 6. 实现现状基线（2026-09-13）

Re.KrtC 的 KRO 本机后端已经实现 `unsafe(using krt.mem, ...;)`、类型化指针、
真实栈分配、函数指针及可空指针模式收窄。具体语法与行为见 `Lang_Spec.md` 的 unsafe 指针章节。
目前强制的是操作权限与类型规则，允许在 unsafe 中访问调用者传入的指针、参数和全局变量。
§2.3 的块外内存禁止访问、生命周期/逃逸分析以及完整命名空间内部函数白名单尚未实现；
不能把这些设计条目当作当前编译器提供的保证。`stackalloc` 空间在函数返回时失效。

| 设施 | 状态 | 位置 |
|---|---|---|
| mmap 合成分配(`new T[n]`、数组字面量、串拼接) | ✅ 可用 | IrGen.c `irgen_allocate_memory`，16 字节头保持负载对齐，指针前 8 字节保存总分配大小 |
| munmap 合成释放 | ✅ 可用 | IrGen.c `irgen_free_memory`(读头取大小) |
| `delete` 语句 | ⚠️ 仅析构+free;缺失析构会被静默合成空析构(待 §5.4 裁决) | IrGen.c ~1998 |
| Memory 标准库 Allocate/Free/Copy/Set | ✅ 可用(mmap/munmap/字节循环) | libs/System/Memory.krt |
| 定长读写原语(1/2/4/8/16 字节) | ✅ 可用 | KrtIrLoadPtrSized / ArrayStoreSized + 局部类型追踪 |
| `KrtMalloc/KrtFree/KrtStackAlloc` 内建名 | 👻 幽灵:有名字无实现,调用即链接炸弹 | 待三块制定位后或删或接 |
| 后台 GC | ❌ 无(且按本设计**永不引入**) | — |
| `using` 资源管理语句(规范旧承诺) | ❌ 词法/解析半成品,语义未接 | 待 §5.4 一并裁决 |

2026-09-13 起，合成堆分配的头部从 8 字节扩为 16 字节，以满足 `int128` 等值的对齐要求。
读取大小、计算数组长度与释放内存的代码已同步更新；跨模块共享这些分配时，旧 `.kro` 必须重新编译，不能混用两种头部布局。


| 本次接入设施 | 当前行为 |
|---|---|
| `&x` / `*p` / `p[i]` | 地址可见的存储槽、按元素大小读写，保留其余整数的寄存器打包 |
| `T*` / `T**` / `void*` | 层级类型检查、步长算术、显式指针转换 |
| `stackalloc T[count]` | 函数栈分配、16 字节对齐、大小溢出检查、逐页探测 |
| `fn(T, ...) -> R` | 函数地址、签名检查、本机间接调用 |
| `T*?` / `is T* hit` | 空值检查、仅真分支可见的非空绑定 |
