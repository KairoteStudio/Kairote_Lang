# Re.KrtC 内存模型

本文记录 C 版编译器和 `libs/System` 当前可见的内存行为。它不描述尚未实现的 `safe`、`scope` 或后台垃圾回收设计，也不能自动代表 SelfHost 的布局。

## 托管数组

`new T[count]` 和数组字面量由编译器分配，并带有内部堆头部。当前原生后端使用 16 字节头部：动态数组长度保存在负载地址前 16 字节处，分配总字节数保存在前 8 字节处。内联定长数组使用编译期长度，不使用这个堆头部。该布局供编译器生成的长度读取和释放代码使用，不是应用程序应依赖的稳定 ABI。

编译器可确定长度的托管数组和内联定长数组在读、写和取元素地址时检查索引。负索引或 `index >= length` 会通过 Linux x86-64 `exit` 系统调用以状态码 `70` 结束进程。索引表达式只计算一次；数组赋值先完成地址和边界检查，再计算右侧表达式。空数组引用的解引用不是有效访问；它仍会触发运行时故障。

堆对象由程序显式释放。对仍在使用的引用执行 `delete`、重复释放或保留已释放对象的别名，都不能由通用垃圾回收机制补救。

## 裸内存和指针

`Memory.Allocate` 返回原始内存区域，不附带托管数组头部。`ArrayOps` 明确要求编译器分配、带有效数组头部的数组；不能把 `Memory.Allocate` 的结果传给它。

裸指针访问需要遵循 `unsafe(using krt.mem;)` 的编译器权限规则。裸指针没有长度元数据，编译器不会对 `p[index]` 执行数组边界检查。`stackalloc` 的地址只在当前函数栈帧期间有效，不能在函数返回后继续使用。

## 字符串

字符串是零结尾字节序列。`libs/System/String.krt` 中的长度、查找和切片以字节为单位。字符串字面量与库创建的字符串有不同的所有权来源；不要对借用的字符串字面量调用释放操作。

库中返回新分配字符串的方法会在对应源码注释中说明释放方式。`StringOps` 的字符串分配需依据其字节长度和结尾零字节释放；`Convert.ToString(bool)` 返回借用的布尔字面量。逐个 API 的所有权注释以 `libs/System/` 源码为准。

## 资源管理原则

- 为 `new` 创建的数组或对象安排一次匹配的 `delete`。
- 对 `Memory.Allocate` 成功返回的地址，按分配大小调用 `Memory.Free`；优先使用 `TryFree` 检查参数是否有效。
- 不要把裸内存误认为托管数组，也不要从内部头部偏移推断应用层对象布局。
- 指针别名和栈借用的生命周期由调用方负责。

当前没有后台 GC；自动释放块和基于词法作用域的生命周期管理不是 Re.KrtC 已实现的语言保证。
