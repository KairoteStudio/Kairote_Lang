# Fibonacci 性能退化定位与修复

本文引用的原始结果、生成源码副本、汇编、IR 快照和日志均在本地归档，不随 PR 提交。 测量数值与构建哈希属于文中记录的历史版本，不代表后续规范整改后的新测量。

用户指出 fib35 曾约为 110 ms，而首次运行测试得到 159.66 ms。为定位差异，将相同的朴素递归源码交给三个编译器版本，在同一机器上交替运行，每个版本、每个输入各 10 次，取算术平均值。代码仍为 `Fib(n - 1) + Fib(n - 2)`，没有改为循环、尾递归或记忆化。

## 对照结果

2026-09-12，AMD Ryzen 9 8945HX，Linux x86-64。测试计时不含编译和进程启动。

| 编译器版本 | fib35 平均耗时 | fib40 平均耗时 | Fib 函数静态指令数 |
|---|---:|---:|---:|
| 新增偶数整数位宽之前的 Git 版本 | 63.699 ms | 687.293 ms | 44 |
| 本次修复前，已含位宽扩展和寄存器分配 | 165.443 ms | 1752.660 ms | 169 |
| 本次修复后 | **61.998 ms** | **665.810 ms** | **74** |

原始数据、每次运行的结果及编译器 SHA-256 见 `FibComparison.json`。同时记录的平均进程 CPU 时间分别为 fib35 的 63.845 / 165.501 / 62.148 ms，以及 fib40 的 687.315 / 1752.540 / 665.951 ms，与墙钟耗时接近。

这里的旧 Git 版本从 `f54a9b459142b9a0deb8efc58daa1119586dd979` 导出后单独构建；修复前版本来自保存的编译器副本。它们用于同环境对照，不能据此确定用户之前 110 ms 那次运行的具体环境和源码版本。此次对照确认了新增整数支持后的代码生成开销，并验证修复恢复了性能。

## 原因与改动

[KroInteger.inc](../../Re.KrtC/src/compiler/Backend/Kro/KroInteger.inc) 原先对普通 `int32` 运算也装载、扩展 `RDX` / `R8` 高位，而实际算术只用低 64 位；读参数、执行运算、转换和保存结果时还反复生成移位扩展序列。[KroRegisterPacking.inc](../../Re.KrtC/src/compiler/Backend/Kro/KroRegisterPacking.inc) 对独占寄存器的变量也执行掩码合并。

修复让普通整数运算、复制、转换、条件和返回只处理必要的低位；8 / 16 / 32 位截断与扩展使用原生 `movsx` / `movzx` / `movsxd` 等指令。独占寄存器的位段写入直接移动，共享位段仍保留掩码合并，超过 64 位的整数仍保留高位计算。移位的计数和宽整数条件单独保留必要的高位检查。

整数专项 12 项通过；性能回归现有 10 项，包括新增的普通整数冗余高位指令检查。2026-09-12 后续修复完成后，完整语法审计为 **75/75 通过**。

## 复现

保存修复前编译器，构建当前编译器后，从项目根目录运行：

```sh
python3 Test/Performance/FibComparison.py --rounds 10 \
  --baseline before_fix /path/to/saved/KrtC
```

可用 `--baseline` 增加其他版本，`--n 35` 只测试 fib35，`--cpu N` 固定测试进程的 CPU。默认串行、轮换版本顺序，不预热、不剔除样本。
